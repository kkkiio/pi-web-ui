## 3. 你说的 Split-Brain 问题确实存在

你的推理是对的。这里必须区分：

**只有一个合法 Owner，不等于物理上绝不可能有两个 Actor 在执行代码。**

比如：

1. Node A 持有 Actor，租约有效。
2. Node A 发生网络分区，无法续租。
3. 租约过期，Node B 通过 CAS 获得所有权。
4. Node A 可能还有尚未结束的代码或外部请求。

celld 针对这个问题设计了两层防护：

- **Self-fencing：** A 租约过期后停止服务。celld 默认租约为 10 秒，还会在请求分发时检查租约是否过期。
- **Fencing Epoch：** 每次所有权转移增加代际编号。A 的旧 Epoch 即使继续产生写入，也不能覆盖 B 所属的新版数据库状态。

此外，celld 在确认数据库写入之前还有持久性与所有权校验，不只是简单的 Lease + CAS。<Cite ref="turn767889view0"/>

但是，你指出的外部副作用问题依然重要。

假设：

```text
Actor A → 发送邮件成功
         → 故障，没能确认任务完成

Actor B → 恢复并重试任务
         → 再次发送相同邮件
```

这甚至不需要两个 Actor 同时执行就可能发生。

对于邮件、支付、第三方 API：

- 使用业务 ID 做幂等；
- 如果外部系统支持 fencing token，可以携带 Epoch，并拒绝旧 Epoch；
- 如果外部系统不支持幂等，单靠 Durable Objects 就无法严格保证 exactly-once。

## 4. 我的进一步判断

我认为可以把这类系统的一致性分成三层：

| 层次 | 能保证什么 |
|---|---|
| Ownership | 同一时刻只有一个被认可的合法 Owner |
| Storage | 旧 Owner 不能污染新 Owner 的持久状态 |
| External Effects | 必须通过额外机制防重复、防过期执行 |

前两层是 celld 运行时重点解决的问题，第三层依然属于应用架构。

**所以我会把 Durable Objects / Orleans 理解为：把分布式状态管理和生命周期管理标准化的框架，而不是彻底解决分布式一致性的框架。**

它真正厉害的地方，是让绝大多数业务只需要面对一个逻辑上的单写者，而不用每个团队都重复实现分片、租约、故障恢复和状态迁移。

但一旦涉及跨 Actor 事务、热点对象或者不可逆的外部副作用，分布式系统的基本约束仍然存在。

你前面从 CAS 一直推导到网络分区、双 Actor 执行和外部副作用，实际上已经抓住了这套设计最重要的工程边界。

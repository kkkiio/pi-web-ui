Anthropic 的 `cache_control` 可以放在 **4 类位置**，通过这些位置来指定缓存断点（Cache Breakpoint）。

注意：**不是通过 `position`、`index` 这样的字段指定位置，而是把 `cache_control` 直接放在你希望缓存结束的那个 Block 上。**

## 1. 支持的位置

| 位置 | JSON 路径 | 用途 |
|---|---|---|
| 请求顶层 | `cache_control` | 自动缓存，自动选择最后一个可缓存 Block |
| 工具定义 | `tools[i].cache_control` | 缓存工具 Schema |
| 系统指令 | `system[i].cache_control` | 缓存 System Prompt |
| 消息内容 | `messages[i].content[j].cache_control` | 缓存对话历史、文档、图片、工具调用及结果 |

其中，`messages.content` 支持 User 和 Assistant 中符合条件的 Block，但不能直接在 `thinking` Block 或内部的 Citation 子结构上设置缓存断点。<Cite refs={["turn775788search4","turn775788search0"]}/>

## 2. 一个完整示例

下面在三个位置分别设置缓存断点：

<CodeBlock language="json" editable>
{
  "model": "claude-sonnet-5-5",
  "max_tokens": 1024,
  "tools": [
    {
      "name": "search",
      "description": "Search documents",
      "input_schema": {
        "type": "object",
        "properties": {
          "query": {"type": "string"}
        },
        "required": ["query"]
      },
      "cache_control": {"type": "ephemeral"}
    }
  ],
  "system": [
    {
      "type": "text",
      "text": "You are a document analysis assistant.",
      "cache_control": {"type": "ephemeral"}
    }
  ],
  "messages": [
    {
      "role": "user",
      "content": [
        {
          "type": "text",
          "text": "Long reusable document...",
          "cache_control": {"type": "ephemeral"}
        },
        {
          "type": "text",
          "text": "Summarize chapter 3."
        }
      ]
    }
  ]
}
</CodeBlock>

注意这里的三个断点并不是分别缓存三个独立片段，而是依次缓存越来越长的 **Prefix（前缀）**：

这意味着：如果用户下一次只是换了问题，而工具、系统指令、文档没有改变，就可以命中之前缓存的前缀。

## 3. 几个重要限制

- **最多 4 个缓存断点**，顶层自动缓存也会占用一个断点名额。
- 默认 TTL 是 **5 分钟**，可以设置 `"ttl": "1h"` 使用 1 小时。
- 缓存的是从请求起点到断点的**完整前缀**，不是仅缓存带有 `cache_control` 的 Block。
- 必须满足模型对应的最小 Token 要求，过短的内容不会产生实际缓存命中。
- 相同的前缀需要保持一致；修改工具定义可能使所有后续缓存失效。<Cite ref="turn538645view0"/>

## 4. 与 OpenAI Prompt Caching 的区别

这里是一个很关键的设计差异。

| OpenAI Prompt Caching | Anthropic Prompt Caching |
|---|---|
| 系统自动识别可缓存前缀 | 可以自动，也可以显式标记断点 |
| 不需要在消息 Block 上加缓存字段 | 支持 `cache_control` 精确标记 |
| 可使用 `prompt_cache_key` 等辅助参数 | 通过 Block 位置和前缀内容控制缓存 |
| 通常不需要自己管理断点 | 最多可以显式管理 4 个断点 |

**我的建议：** 如果你是在开发统一 LLM API 网关，可以把 Anthropic 的 `cache_control` 视作一种 *Prefix Checkpoint Marker*（前缀检查点标记），而不是某个消息的普通元数据。

它表达的语义实际上是：**“把整个 Prompt 从开头到这里，作为一个可复用的缓存前缀。”**

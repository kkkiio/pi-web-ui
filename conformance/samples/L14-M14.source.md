## 三、celld 是如何实现 Durable Objects 的？

Cloudflare 已经提供了 Durable Objects，为什么 Ryan Dahl（Node.js、Deno 的创造者）还要做 celld？

因为 Cloudflare 的 Durable Objects 很好用，但底层是由 Cloudflare 托管的。

**celld 想把 Durable Objects 从一种云厂商服务，变成一种可以部署在任何服务器上的基础架构能力。**

它采用了一个挺巧妙的组合：

它的设计有三个关键点。

### 1. 每个 Cell 都有自己的 SQLite

在 celld 的术语中，一个 Durable Object 就是一个 **Cell**。

例如 `room-123` 内部有一份 SQLite，`room-456` 有另一份 SQLite。

不同 Cell 的数据彼此隔离。

这样业务自然按照对象分片，而不需要先设计一个庞大的共享数据库。

### 2. 用对象存储协调所有权

假设 `room-123` 正在 Node A 上运行。

Node A 会在 S3 中持有一个所有权记录（Ownership Record），带有租约（Lease）和代际编号（Epoch）。

如果 Node A 宕机：

Node B 可以在租约失效后通过条件写入（Compare-and-Swap）获得该 Cell 的所有权，恢复 SQLite 状态，然后继续服务。

Epoch fencing 用来防止旧节点恢复后以过期身份继续对外确认写入。

**巧妙的地方是：celld 不需要你额外部署 ZooKeeper、etcd 或专用的共识服务来管理这些 Cell。**

但这不代表完全没有分布式协调。它实际上把关键的所有权仲裁交给了支持强一致条件写入的对象存储。<Cite refs={["turn881513view0","turn340484search6"]}/>

### 3. 通过 LTX 复制 SQLite 的变更

在多节点模式下，celld 可以把已经提交的数据库变化复制给其他节点。

默认情况下，如果有可用的副本节点，它会等副本把数据持久化到磁盘，然后才确认写入成功；后台再上传到对象存储。

单节点没有副本时，则需要先把写入持久化到 bucket。

这是它实现 **RPO=0（已确认写入的恢复点目标为零数据丢失）** 的设计。这个保证依赖符合要求的对象存储、节点持久化和恢复协议，并不意味着任何基础设施灾难下都绝对不会丢数据。<Cite refs={["turn340484search2","turn881513view0"]}/>

## 四、两个实际应用场景

### 场景 1：多人实时聊天 / 协作房间

<AsyncImageGroup query={["modern team collaboration chat web application interface multiple participants channels messages clean UI","collaborative online whiteboard web app realtime cursors multiple users interface"]} aspectRatio="5:3" layout="carousel"/>

假设你要开发一个类似 Discord 的实时聊天室。

有 100 万注册用户、10 万个聊天房间，但一个房间通常只有 5～50 个人在线。

你可以给每个房间创建一个 Durable Object：

`room-123` 负责处理它的聊天消息、在线状态、WebSocket 连接和消息广播。

请求路由在代码层面可以非常简单：

```ts
const room = env.ROOMS.getByName("room-123");

await room.sendMessage({
  userId: "alice",
  text: "Hello!"
});
```

其中 `sendMessage` 是你在 Durable Object 类中实现的 RPC 方法。

当 Alice 发送消息后，Room Object 可以把消息写入自己的 SQLite，再向当前连接的用户广播。

即使 50 个人同时发送消息，也由一个逻辑对象负责这个房间的状态。

聊天室没人在线时，Durable Object 可以休眠；如果符合 WebSocket Hibernation 条件，Cloudflare 还可以让对象休眠而保留相关连接的唤醒能力。

**真正的优势：你的程序基本上按照“一个聊天室就是一个对象”去写，而不需要先组装 WebSocket 网关、Redis Pub/Sub、数据库和多个协调组件。**

当然，聊天记录搜索、跨房间分析等需求，仍可能需要外部系统。

### 场景 2：每个用户拥有一个长期存在的 AI Agent

<AsyncImageGroup query={["AI personal assistant task dashboard interface dark modern web app agent memory activities","AI agent workflow application interface tasks tools timeline automation dashboard"]} aspectRatio="5:3" layout="carousel"/>

这个场景也许更有意思，而且正是 Ryan Dahl 在最新公告中特别强调的方向。<Cite ref="turn340484search0"/>

假设你提供一个 AI 助手 SaaS，拥有 10 万用户。

每个用户都有一个 AI Agent，负责管理自己的任务状态、对话上下文、待处理工作和定时提醒。

你可以采用：

`agent:user-001` → 一个 Durable Object

`agent:user-002` → 另一个 Durable Object

每个 Agent Object 拥有自己的 SQLite，用于记录对话历史、执行状态、任务队列等。

这跟传统的无状态 AI API 有显著不同。

传统 API 往往是：收到请求 → 从外部数据库加载上下文 → 执行 → 写回 → 退出。

Durable Object 则允许你把 Agent 设计成一个**拥有固定身份和持续状态的服务对象**。

但注意，它不是一台永远运行的虚拟机。对象可能重启、休眠，正在进行的外部 API 调用也不一定能跨故障恢复。所以关键执行进度必须持久化，耗时任务也需要拆分成可恢复步骤。

这对 Agent 的编排和状态管理很有价值，尤其适合需要同时管理大量独立 Agent 的系统。

## 五、它和传统后端架构如何比较？

| 维度 | 传统 Worker + 数据库 | Durable Objects |
|---|---|---|
| 核心模型 | 无状态请求处理 | 有身份的状态对象 |
| 状态管理 | 外部共享数据库 | 对象私有存储 |
| 并发协调 | 数据库事务、锁等 | 单对象写者 + 事务 |
| WebSocket | 需要独立协调设计 | 可以由对象管理 |
| 水平扩容 | 扩容服务实例 | 增加对象数量 |
| 主要限制 | 数据库或共享服务瓶颈 | 单个热点对象的吞吐瓶颈 |

再看 Cloudflare 与 celld：

| | Cloudflare Durable Objects | celld |
|---|---|---|
| 部署方式 | Cloudflare 托管 | 自己部署 |
| 数据存储 | Cloudflare 管理的持久存储 | 私有 SQLite + 自有对象存储 |
| 故障恢复 | 平台自动管理 | celld 协议 + 自有节点 |
| 地理分布 | Cloudflare 全球网络 | 取决于你的节点部署 |
| 运维负担 | 低 | 你自己负责 |
| 当前成熟度 | 正式云服务 | Beta，仍有限制 |

celld 当前文档标记为 v0.6.2 Beta，还需要自行配置 TLS、私有节点通信、安全策略和部署入口。因此“可自托管”不等于“生产环境零运维”。<Cite ref="turn881513view1"/>

## 六、它最大的局限是什么？

我觉得有三个点值得格外注意。

**第一：一个热点对象不会自动变成多写者集群。**

例如一个直播房间里有 100 万人同时发消息，单个 Durable Object 可能成为吞吐瓶颈。

你还是需要按照用户、分区或者消息类型进一步拆分。

**第二：强一致性的边界是单个对象。**

`room-123` 内部可以方便地保证状态一致，但如果你想在 `room-123` 与 `room-456` 之间做原子事务，Durable Objects 并不会自动帮你实现跨对象事务。

**第三：它不是所有数据库和后端服务的替代品。**

订单搜索、跨用户报表、大规模 SQL JOIN、数据仓库、全局事务等需求，仍然更适合专门的数据库或分析系统。

而且 Durable Objects 也不自动保证外部 API 调用 exactly-once（恰好一次）。例如已经扣款但在保存结果前崩溃，你仍需要幂等键等机制。

## 七、我认为真正值得关注的理念

Durable Objects 的一个重要创新，是把分布式系统的基本组织单位从 **Service（服务）** 变成更细粒度的 **Stateful Object（有状态对象）**。

传统架构里，你可能先部署 10 个服务副本，再思考这 10 个副本如何共享和协调状态。

Durable Objects 反过来：

**先确定业务中天然独立的状态边界，再让平台决定这些对象应该在哪里运行、何时启动、如何持久化以及故障后如何恢复。**

这有点像把 Actor Model、Serverless、SQLite 和自动化资源调度组合在了一起。

而 celld 的意义在于：这种编程模型有机会从 Cloudflare 的专有托管能力，发展为能在自有基础设施上运行的通用抽象。

**一句话总结：以前我们把数据放进数据库，让一群无状态服务器来处理它；Durable Objects 让每份独立的业务状态，拥有自己的计算入口和持久化能力。**

这不是让分布式系统的复杂性消失，而是让平台承担其中一大部分，让开发者能更直接地围绕业务对象编程。

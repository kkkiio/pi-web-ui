## 一、社区有没有真正截获 ChatGPT 的 UI 输出？

这一轮我重点搜索了 GitHub、Reddit、Hacker News、中英文技术文章，以及 ChatGPT 的相关逆向工程项目。

结果如下：

| 证据 | 找到了什么 | 可信度 |
|---|---|---|
| OpenAI 官方 | 原生组件库、流式编译器、UI 专项训练 | 高 |
| Reddit 用户实验 | 有人通过提示词测试出不同的交互界面行为 | 中低 |
| ChatGPT 原始网络响应 | **没有找到可公开复核的 Intelligent UI HAR/SSE 样本** | 尚无证据 |
| 解码后的完整组件 Schema | 没找到 | 尚无证据 |
| ChatGPT 前端渲染器逆向 | 没找到针对新版 Intelligent UI 的可靠完整分析 | 尚无证据 |
| 第三方类似渲染器 | 找到了开源项目，但不是 OpenAI 原始实现 | 高 |

### 最值得追踪的 Reddit 线索

2026 年 9 月 23 日，一位用户发帖称，ChatGPT 在某些 Thinking 配置下突然开始输出复杂的交互式 UI。

他测试过注意力矩阵、细胞结构图等，还提供了两段公开共享对话：

- <Link url="https://www.reddit.com/r/ChatGPT/comments/1woem9i/chatgpt_is_suddenly_generating_interactive_uis/" title="Reddit 原帖与评论"/>
- <Link url="https://chatgpt.com/share/6ab422ab-10e4-83ed-b515-a954ac82e74c" title="交互式细胞解释示例"/>
- <Link url="https://chatgpt.com/share/6ab42304-3834-83eb-b065-6fc39a302198" title="传统文本版本"/>

他还声称模型把这种交互界面与一个叫 **DIL（Dynamic Interface Language）** 的名称关联起来。

但这里需要谨慎：这属于用户通过模型回复获得的名称，**并不是网络抓包发现的协议标识**。模型可能把提示词理解成某种内部功能，也可能只是顺着上下文生成解释。<Cite ref="turn368884view0"/>

10 月 8 日，Hacker News 的 GPT-6 发布讨论中，也有开发者直接询问流式 UI 库和输出格式的细节，但我没有找到提供原始协议内容的可靠回答。<Cite ref="turn173163view4"/>

因此，现在不能负责任地给出一份所谓「OpenAI Intelligent UI 完整 DSL 语法」。

### 另一个 GitHub 线索

<text weight="medium"><Link url="https://github.com/Gan-Tu/Widgets" title="Gan-Tu / Widgets"/></text>

这是一个独立的开源 Widget Renderer，提供大量预定义组件、受限模板语言、数据绑定、局部状态和声明式 Action，并支持使用 GPT-6 系列生成 Widget。

它的架构与我们讨论的目标很接近：

- 模型生成组件描述。
- Renderer 解析和校验。
- 宿主控制组件实现及交互行为。

不过，作者明确把它定位为 OpenAI ChatKit Widgets 的开源替代品，而不是 OpenAI Intelligent UI 的原始协议实现。因此，**不能把它的组件表当作 GPT-6 的训练组件表**。<Cite ref="turn712455view0"/>

## 二、目前能确认 Intelligent UI 有哪些组件？

我们需要区分「用户看到了哪种界面」与「模型实际输出了哪种组件标识」。

OpenAI 公开确认的能力范围如下：

| UI 能力 | 公开证据 | A2UI 复刻难度 |
|---|---|---|
| 文本、图片、卡片式布局 | 官方示例 | 低 |
| 按钮、表单与参数输入 | 官方说明 | 低 |
| 多项对比与步骤展示 | 官方说明 | 低 |
| 可调整参数的计算器 | 官方演示 | 中 |
| 动态图表 | 官方演示 | 中 |
| 交互式结构图 | 官方演示 | 中高 |
| 地图与路线信息 | 官方演示 | 高 |
| 对话中的小游戏 | 官方演示 | 高 |

以上是**功能级别的能力清单，不是底层组件注册表**。例如，地图可能由某个原生地图组件生成，也可能来自单独的工具结果，不能仅凭视觉效果确定。

来源：<Link url="https://openai.com/index/gpt-6-for-everyone/" title="OpenAI 官方发布说明"/>，以及 <Link url="https://www.wired.com/story/openai-chatgpt-intelligent-ui-is-more-show-than-tell" title="WIRED 的实际体验"/>。<Cite refs={["turn646274search0","turn549741news43"]}/>

目前仍然缺少精确组件名称、参数 Schema、数据绑定方式、客户端状态管理方式，以及 Action 能调用哪些宿主功能的公开完整资料。

这恰恰是复刻工作最大的技术不确定性。

但 A2UI 的 Custom Catalog 可以定义这些组件以及对应的函数。官方也建议生产环境使用自己的 Catalog 来表达产品的设计系统。<Cite refs={["turn837849search0","turn837849search7"]}/>

### 因此，完全可以设计一个 ChatGPT-like Catalog

以下是我建议定义的业务组件类型，而不是声称 OpenAI 内部就是这些名称：

| 自定义 A2UI 组件 | 主要能力 |
|---|---|
| `InteractiveChart` | 折线、柱状、散点以及图表联动 |
| `GeoMap` | 地图、地点、路线 |
| `DataTable` | 表格、排序、筛选 |
| `InteractiveDiagram` | 节点关系、部件选择、动态标注 |
| `ParameterPanel` | 输入控件与计算结果联动 |
| `MediaExplorer` | 图片、视频与内容选择 |
| `MiniApp` | 受限的局部状态和自定义交互 |

其中比较简单的只是包装现有组件；比较复杂的还需要你自己实现对应的客户端组件、状态系统与 Action 处理。

**光在 Catalog 里注册一个 `InteractiveChart` 名称，并不意味着模型自动知道如何正确生成它，更不意味着客户端自动有图表渲染能力。**

A2UI 现有协议支持 `createSurface`、`updateComponents`、`updateDataModel`、`deleteSurface` 等流式消息类型，并使用组件 ID 引用、数据模型和 Action 来维护界面。<Cite ref="turn487587view4"/>

这个架构中可以比较两种方案：

**方案 A：直接生成 A2UI。** 给 GPT-6 Custom Catalog、Schema、组件示例，让模型直接生成 A2UI 消息。这最容易落地，也应该作为基线。

**方案 B：先生成适合模型的 UI 中间表示，再转换成 A2UI。** 这种方式允许模型更自然地组织嵌套布局，转换器负责展平组件树、分配 ID、生成状态绑定和流式更新。

B 是否真正优于 A，目前没有证据。它只是基于你的训练分布假设提出的工程实验。

另外，有一个非常重要的限制：**OpenAI 这次的 Intelligent UI 属于 ChatGPT Chat 产品。官方没有把它作为独立的 UI API 发布。** 即使通过 API 使用 GPT-6 Sol，也不能假定会获得与 ChatGPT 内相同的训练版本、提示上下文、组件约束和编译器能力。<Cite refs={["turn646274search0","turn359167search4"]}/>

这可能比两个 DSL 本身的差异影响更大。

## 五、要验证这个假设，应该怎样抓包和实验？

我建议把研究拆成两个阶段。

### 阶段 1：确认 ChatGPT 真正发送什么

在自己的 ChatGPT Web 会话中，可以使用浏览器开发者工具进行授权范围内的检查。

建议测试三类请求：

1. **纯布局：**「比较三种相机，生成交互式对比界面」
2. **状态交互：**「生成一个可调整本金、利率和期限的储蓄计算器」
3. **复杂渲染：**「生成一张可点击身体器官的交互式结构图」

重点同时记录：

- 浏览器 Network 面板中的响应内容和增量消息。
- UI 在页面中逐步出现的顺序。
- 用户改变输入值时，是否发生新的网络请求。
- 按钮 Action 是本地执行，还是触发服务器事件。
- 同一任务在普通文本和 Intelligent UI 下的网络差异。

如果浏览器使用流式 Fetch，普通 Network 面板可能不方便逐事件阅读。可以使用支持 Fetch Stream 的调试工具辅助观察，但应先审核扩展权限。

**注意：抓到浏览器网络格式，不一定等于抓到了模型原始 token 输出。** 服务端可能已经进行了协议转换或组件编译。

分享 HAR 时要删除 Cookie、Authorization、会话标识和私人对话内容。

### 阶段 2：验证训练优势能否迁移

用完全相同的任务比较三种路径：

| 实验组 | 输出方式 | 验证目的 |
|---|---|---|
| A | GPT-6 直接生成 A2UI | 基础能力 |
| B | GPT-6 生成自定义中间 UI，再编译成 A2UI | 中间层是否提升成功率 |
| C | ChatGPT Intelligent UI 作为参考 | 原生体验差距 |

这里不要只看 JSON Schema 通过率。

更重要的是：模型是否选择合适组件、生成的交互是否真的可用、多轮修改能否保持状态，以及端到端渲染延迟和 Token 成本。

如果 B 组持续优于 A 组，而且在相同任务里接近 ChatGPT 的组件选择和交互设计，那就能初步支持你的假设。

## 六、最终判断

目前可以明确区分三个结论：

<box gap={2}>
  <row align="start" gap={2}>
    <icon name="check-circle-2" color="success" size="lg"/>
    <box flex="1">
      **A2UI 技术上支持定义一套类似 Intelligent UI 的组件集合。**

      Custom Catalog、数据模型与客户端 Action 已经提供了实现基础。
    </box>
  </row>
  <row align="start" gap={2}>
    <icon name="circle-help" color="secondary" size="lg"/>
    <box flex="1">
      **没有证据证明 GPT-6 API 对原生 UI 表示的熟悉程度能够直接迁移。**

      ChatGPT 产品侧的训练、上下文和渲染机制可能都是能力的一部分。
    </box>
  </row>
  <row align="start" gap={2}>
    <icon name="search" color="secondary" size="lg"/>
    <box flex="1">
      **还缺少最关键的原始证据：可复核的 ChatGPT Intelligent UI 网络响应与完整组件格式。**

      目前无法声称已经完成协议逆向，也不能据此实现精确转换器。
    </box>
  </row>
</box>

所以我的建议不是马上实现一个「OpenAI 协议兼容层」，而是**先用 A2UI Custom Catalog 做一个小型生成实验，同时对 ChatGPT 的实际 UI 响应开展采样研究**。

这样就能直接验证你真正关心的问题：

**GPT-6 的 Intelligent UI 优势，到底主要来自模型学会了设计界面，还是来自它熟悉一套特定的 UI 表达语言和组件环境？**

这个区别会决定我们应该投资于模型提示与评测、自己的中间 DSL，还是协议适配器。

## 3. 更有意思的是：他参与设计的 ReScript 其实也保留了 `.resi`

这可能是最值得注意的一点。

<Entity category="software" value="ReScript" disambig="静态类型的 JavaScript 编程语言"/> 有一套几乎直接继承 OCaml 的设计：

```text
Button.resi    // 接口
Button.res     // 实现
```

`.resi` 不仅可以指定函数签名，还可以隐藏实现中的成员。ReScript 的官方文档甚至明确说，它可以用来记录一个模块的公开 API。<Cite ref="turn886155search0"/>

但我找到的 ReScript 社区反馈很有启发：

**开发者确实会抱怨接口和实现需要重复维护类型定义。**

2024 年有人专门讨论，为什么 record 类型需要在 `.resi` 和 `.res` 中写两遍。<Cite ref="turn886155search3"/>

另一场讨论里，开发者提到维护两套定义、IDE 支持，以及快速分享单文件代码的体验都会受到影响。<Cite ref="turn886155search7"/>

这说明重复维护不是理论上的成本，而是真实存在的使用痛点。

我怀疑 MoonBit 的选择部分源于这样的权衡：

| 设计选择 | 优点 | 代价 |
|---|---|---|
| 人工编写接口文件 | 接口简洁，适合文档和 Review | 同步维护两份声明 |
| 从实现自动生成接口 | 无须重复维护，接口始终反映实际代码 | 人很难独立决定接口的组织方式 |
| `pub` 控制可见性 | 声明和实现在一个地方，改动直接 | 公开 API 分散在实现文件中 |
| 独立的 `declare` | 可以先设计规格，再交给 AI 实现 | 需要处理声明与实现的重复及生命周期 |

MoonBit 选择将 `pub` 写在定义上，默认函数不对其他 package 公开；随后又提供了 `moon info` 自动生成接口摘要。<Cite refs={["turn886155search2","turn886155search16"]}/>

这更像是：**保留接口摘要的价值，但尽量不让所有开发者都承担双份声明的成本。**

这是我的设计推断，不是 MoonBit 团队公开确认的动机。

## 4. 那为什么最近又引入 `declare`？

这里恰好出现了一个变化：AI 让原本的成本收益关系发生了变化。

以前，维护一个手写声明文件意味着程序员要多做工作。

现在，如果 AI 负责实现、修改和修复编译错误，那么人类单独维护一份短小的规格，可能反而节省时间。

不过，有一个细节能说明 MoonBit 目前的定位：

MoonBit 文档将 `declare` 描述为一种在实现之前固定接口的能力；当它已有实现时，编译器还定义了 `declaration_implemented` 诊断，建议移除冗余声明。该诊断目前默认关闭。<Cite refs={["turn174266search5","turn468731search0","turn468731search1"]}/>

也就是说，这套机制允许你把声明与实现放在不同文件中，但**并没有把长期维护两份声明确立为普通 package 的标准开发方式**。

在我看来，这恰好留下了一块值得实验的空间。

这张图有三个值得关注的地方。

**第一，路由决策发生在 Netfilter Hook 之间。**

例如，一个从网卡收到的转发数据包会经历：

```text
PREROUTING
    ↓
Routing Decision
    ↓
FORWARD
    ↓
POSTROUTING
```

因此不能说 Hook 在路由表上面一层。

**第二，并不是每个包都会经过所有 Hook。**

收到的包如果是给本机的，走 `INPUT`，而不是 `FORWARD`；本机主动发送的包走 `OUTPUT`，不走 `PREROUTING`。

**第三，本机发送时有一个容易忽略的细节。**

本机生成的数据包通常先进行初始路由查找，再经过 `OUTPUT` Hook。如果 `OUTPUT` 中的规则修改了影响路由的字段，内核可能重新执行路由查找。<Cite refs={["turn901100search0","turn449499search13"]}/>

## 四、Hook 和 iptables Rules 到底是什么关系？

现在看你的第二个猜想：

> 策略规则上面是不是还有所谓的 Hook？

这里你的理解方向是对的。

但是中间还差一个重要概念：**Chain（链）**。

以 nftables 为例，可以把组织关系理解成：

<box border radius="xl" padding={3} gap={2}>
  <box background="surface-secondary" radius="md" padding={3} align="center" gap={1}>
    **Netfilter Hook: INPUT**
    <text size="xs" color="secondary">内核网络流程中的执行点</text>
  </box>
  <row justify="center"><icon name="arrow-down" color="tertiary"/></row>
  <box border radius="lg" padding={3} gap={2}>
    <text weight="medium" textAlign="center">Chain: input</text>
    <box background="surface-secondary" radius="md" padding={2}>
      <text size="sm">Rule 1: 已建立连接 → ACCEPT</text>
    </box>
    <box background="surface-secondary" radius="md" padding={2}>
      <text size="sm">Rule 2: TCP 22 端口 → ACCEPT</text>
    </box>
    <box background="surface-secondary" radius="md" padding={2}>
      <text size="sm">默认策略：DROP</text>
    </box>
  </box>
</box>

Hook 可以理解成一个 **内核提供的回调执行点（Callback Point）**。

当数据包经过这个位置时，内核会调用注册在这里的处理逻辑。

iptables 或 nftables 可以将规则链注册到相应 Hook 上。内核中的 conntrack 等模块也可以注册自己的处理逻辑。

再看一段真实的 nftables 配置：

```nft
table inet filter {
    chain input {
        type filter hook input priority 0;
        policy drop;

        ct state established,related accept
        tcp dport 22 accept
    }
}
```

先不用纠结语法，只注意：

```text
hook input
```

它就是在声明：把这条基础链注册到 `INPUT` Hook。

而下面的：

```text
ct state established,related accept
```

则是一条具体的匹配规则。

这里的 `priority 0` 控制同一个 Hook 上不同处理逻辑的执行顺序。较小的优先级数值先执行。<Cite refs={["turn901100search2","turn449499search0"]}/>

所以，到这里你可以把它们整理成：

**Hook → Chain → Rule**

但路由表并不属于这条层级关系，而是由网络协议栈在需要路由决策的地方使用。

## 五、Connection Tracking 又在哪里？

这也是很多人学习 Linux 网络时特别容易混乱的地方。

因为 conntrack 不是一个额外的生命周期阶段，也不仅是一组防火墙规则。

它本质上是一个 **有状态的数据包跟踪子系统**。

举个例子：

```text
客户端 10.0.0.10:50000
        ↓ TCP SYN
服务器 8.8.8.8:443
```

conntrack 可以根据源 IP、目标 IP、传输层协议、端口等信息识别这个网络流，并维护一条连接跟踪记录。

后续回复：

```text
服务器 8.8.8.8:443
        ↓ TCP SYN-ACK
客户端 10.0.0.10:50000
```

conntrack 能识别出：

这是同一条网络流的回复方向，而不是完全无关的新流量。

因此防火墙可以写：

```nft
ct state established,related accept
```

意思是：如果数据包属于已建立或相关的连接，就允许它通过。

conntrack 的状态包括 `NEW`、`ESTABLISHED`、`RELATED`、`INVALID`、`UNTRACKED` 等。它不只适用于 TCP，也可以跟踪 UDP 等协议；而且 conntrack 的 `ESTABLISHED` 不等同于 TCP Socket 自身的 ESTABLISHED 状态。<Cite refs={["turn449499search0","turn449499search5"]}/>

最重要的是理解它与 Hook 的关系：

- conntrack 在 Netfilter 的特定 Hook 上进行数据包跟踪，普通 IPv4 流程中通常在 `PREROUTING` 或 `OUTPUT` 早期处理。
- conntrack 保存动态连接状态。
- iptables/nftables 规则可以读取这些状态，做出放行或丢弃的决定。
- NAT 也依赖 conntrack 记录地址转换关系。

因此，**conntrack 提供状态信息，防火墙规则使用这些信息**，两者并不是同一个东西。

## 六、还有一个你必须区分的东西：Policy Routing

你提到的“策略规则”，在 Linux 中恰好有另一套真正叫做 Policy Routing 的机制。

假设有：

```bash
ip rule show
```

可能输出：

```text
0:      from all lookup local
32766:  from all lookup main
32767:  from all lookup default
```

这表示 Linux 默认存在一组路由策略规则，用来选择路由表。

比如你以后可以配置：

```text
来自 10.0.0.0/8 的流量
    ↓
查询路由表 100

其他流量
    ↓
查询 main 路由表
```

所以，对于路由系统内部而言，确实存在一层选择关系：

```text
Routing Policy Database（ip rule）
             ↓
       Routing Table
             ↓
        选择具体路由
             ↓
      下一跳 + 出口接口
```

这套机制和 iptables 中的防火墙规则是不同的。<Cite ref="turn901100search9"/>

注意，我们现在已经遇到了三种容易混淆的“表”：

| 名称 | 例子 | 用途 |
|---|---|---|
| 路由表 | `ip route` | 查找到目的地的路径 |
| Netfilter 表 | `table inet filter` | 组织规则链 |
| conntrack 表 | 连接跟踪记录 | 保存网络流状态 |

虽然都叫 table，但它们并不是一种通用的表结构，也不属于同一个处理层级。

## 七、现代 Linux 里还需要知道 nftables

你想学现代 Linux 网络栈，所以这里有必要提前说明：

**Netfilter 是内核框架；iptables 是传统的规则管理机制；nftables 是更新的规则管理框架。**

iptables 和 nftables 共享 Netfilter 的 Hook、conntrack、NAT 等底层基础设施，但规则的组织和执行机制不同。

而且在许多 Linux 发行版中，`iptables` 命令实际上可能使用 `iptables-nft` 兼容后端。

因此现在学习时，建议先理解共同的内核数据包路径，再学习 nftables 的规则模型，最后理解传统 iptables 的表和链如何映射到这些概念。<Cite ref="turn901100search0"/>

## 八、用一次实验把这些概念连接起来

你可以在 Linux 上执行下面这些只读命令：

```bash
# 1. 查看路由策略规则
ip rule show

# 2. 查看主路由表
ip route show table main

# 3. 查询到某个目标地址时内核会怎样选路
ip route get 8.8.8.8

# 4. 查看 nftables 规则
sudo nft list ruleset

# 5. 查看 conntrack 记录（需安装 conntrack 工具）
sudo conntrack -L
```

你可以把这五个命令分别理解成：

**谁决定查哪张路由表？表里有什么？具体选了哪条路？哪些 Netfilter 规则会处理包？内核记住了哪些连接状态？**

这五个问题共同组成了你想理解的 Linux 网络栈的一大部分。

## 九、最后帮你建立一个清晰的心智模型

我建议你以后不要把这套机制想象成一个垂直的三层结构，而是记住两个维度：

**维度 A：数据包在内核中经过哪些位置？**

`PREROUTING → Routing → INPUT / FORWARD → POSTROUTING`

或者，本机发送时：

`Routing → OUTPUT → POSTROUTING`

**维度 B：内核在这些位置使用哪些机制？**

- 路由：选择路径、下一跳、出口设备。
- Netfilter：在 Hook 处执行注册的处理逻辑。
- nftables / iptables：提供可配置的数据包处理规则。
- conntrack：保存网络流的状态，供防火墙和 NAT 等机制使用。

我建议我们下一步不要立刻研究所有 iptables 表和规则，而是专门深入一个问题：

**为什么 DNAT 要在 PREROUTING，而 SNAT 通常在 POSTROUTING？**

这个问题能很好地把你已经理解的路由查找与 Netfilter Hook 联系起来。一旦理解了 NAT 和路由决策的先后关系，再看 `iptables` 的 `raw`、`mangle`、`nat`、`filter`，以及 conntrack 的执行顺序，就会清晰得多。

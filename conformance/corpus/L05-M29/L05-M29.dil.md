## 五、Tool Calling：与 OpenAI 的最大实践差异

这是我最建议你仔细理解的部分，因为实际开发 Agent 时，最容易在这里遇到协议兼容问题。

假设你想让 Claude 调用一个查询天气的函数。

### 1. 定义工具

在 Anthropic 请求中，工具定义类似这样：

<CodeBlock language="json">
{
  "name": "get_weather",
  "description": "Get weather for a city.",
  "input_schema": {
    "type": "object",
    "properties": {
      "city": {
        "type": "string"
      }
    },
    "required": ["city"]
  }
}
</CodeBlock>

与 OpenAI 的工具定义相比，主要区别是：

| OpenAI Chat Completions | Anthropic Messages |
|---|---|
| `type: "function"` | 自定义工具不需要这一层 |
| `function.name` | `name` |
| `function.description` | `description` |
| `function.parameters` | `input_schema` |

本质上都用 JSON Schema 描述工具参数。

### 2. Claude 决定调用工具

假设用户问：

> What's the weather in Tokyo?

Claude 可能返回：

<CodeBlock language="json">
{
  "content": [
    {
      "type": "tool_use",
      "id": "toolu_123",
      "name": "get_weather",
      "input": {
        "city": "Tokyo"
      }
    }
  ],
  "stop_reason": "tool_use"
}
</CodeBlock>

注意两点：

- 工具参数 `input` 是 JSON 对象，而 OpenAI Chat Completions 的 `function.arguments` 通常是 JSON 字符串。
- `stop_reason: "tool_use"` 告诉你的程序需要执行工具，而不是把当前内容当成完整的最终回答。

### 3. 执行工具并返回结果

你的程序执行 `get_weather("Tokyo")`，假设获得 `22°C, Sunny`。

然后需要把工具调用结果放在一个 **`role: "user"` 的消息**里：

<CodeBlock language="json">
{
  "role": "user",
  "content": [
    {
      "type": "tool_result",
      "tool_use_id": "toolu_123",
      "content": "22°C, Sunny"
    }
  ]
}
</CodeBlock>

下一次请求要包含原来的对话历史、Claude 返回的 `tool_use` 消息，以及这条 `tool_result` 消息。

这里很容易踩坑：

**Anthropic 没有像 OpenAI Chat Completions 那样用独立的 `tool` 角色承载工具结果。**

工具结果被包装成一个 `user` Message 的 Content Block。

可以用下面的交互流程来理解：

<box border radius="lg" padding={3} gap={2}>
  <box align="center" gap=1>
    <box background="surface-secondary" padding={{x:3,y:2}} radius="md" width="90%">
      <text textAlign="center" weight="medium">1. Client → Claude</text>
      <text textAlign="center" color="secondary" size="xs">发送 messages + tools</text>
    </box>
    <icon name="arrow-down" color="tertiary"/>
    <box border radius="md" padding={{x:3,y:2}} width="90%">
      <text textAlign="center" weight="medium">2. Claude → Client</text>
      <text textAlign="center" color="secondary" size="xs">tool_use / stop_reason: tool_use</text>
    </box>
    <icon name="arrow-down" color="tertiary"/>
    <box background="surface-secondary" radius="md" padding={{x:3,y:2}} width="90%">
      <text textAlign="center" weight="medium">3. Client 执行工具</text>
      <text textAlign="center" color="secondary" size="xs">运行函数，获取返回值</text>
    </box>
    <icon name="arrow-down" color="tertiary"/>
    <box border radius="md" padding={{x:3,y:2}} width="90%">
      <text textAlign="center" weight="medium">4. Client → Claude</text>
      <text textAlign="center" color="secondary" size="xs">附带历史与 tool_result</text>
    </box>
    <icon name="arrow-down" color="tertiary"/>
    <box background="surface-secondary" radius="md" padding={{x:3,y:2}} width="90%">
      <text textAlign="center" weight="medium">5. Claude → Client</text>
      <text textAlign="center" color="secondary" size="xs">生成回答，或继续调用工具</text>
    </box>
  </box>
</box>

你可以将它视为一个经典的 Agent Loop：

```python
while True:
    response = call_claude(messages, tools)

    messages.append({
        "role": "assistant",
        "content": response.content
    })

    if response.stop_reason == "tool_use":
        results = execute_tool_calls(response.content)
        messages.append({
            "role": "user",
            "content": results
        })
        continue

    break
```

这是展示流程的伪代码，`call_claude` 和 `execute_tool_calls` 需要由你实现，也要处理多工具调用及异常情况。

另外，Anthropic 还区分：

- **Client Tools**：你的应用程序负责执行，比如 `get_weather`。
- **Server Tools**：Anthropic 负责执行，比如官方的 Web Search、Web Fetch 等工具。

对于 Server Tools，你通常不需要自行处理 `tool_result` 往返。<Cite refs={["turn919162search1","turn919162search6"]}/>

## 六、Streaming：都是 SSE，但事件协议不一样

如果你熟悉 OpenAI Chat Completions 的流式模式，应该知道它经常返回这样的数据：

```text
data: {"choices":[{"delta":{"content":"Hello"}}]}

data: {"choices":[{"delta":{"content":" world"}}]}

data: [DONE]
```

Anthropic 也是使用 SSE（Server-Sent Events），但其协议显式区分 Message 事件和 Content Block 事件。

一个典型的流式生命周期为：

<box border radius="lg" padding={3} gap={2}>
  <list marker="number" connector="solid" gap={2}>
    <list-item>
      **`message_start`**

      <text size="sm" color="secondary">创建 Message，通常含有空的 `content[]`。</text>
    </list-item>
    <list-item>
      **`content_block_start`**

      <text size="sm" color="secondary">开始生成一个 Block，比如文本或工具调用。</text>
    </list-item>
    <list-item>
      **`content_block_delta`**

      <text size="sm" color="secondary">持续收到文本或结构化参数的增量。</text>
    </list-item>
    <list-item>
      **`content_block_stop`**

      <text size="sm" color="secondary">当前 Block 结束。可能继续出现下一个 Block。</text>
    </list-item>
    <list-item>
      **`message_delta`**

      <text size="sm" color="secondary">更新 Message 的最终状态，比如 `stop_reason` 和 Token 使用量。</text>
    </list-item>
    <list-item>
      **`message_stop`**

      <text size="sm" color="secondary">整个消息生成结束。</text>
    </list-item>
  </list>
</box>

例如，一段极简的 Anthropic SSE：

<CodeBlock language="text">
event: content_block_start
data: {"type":"content_block_start","index":0,"content_block":{"type":"text","text":""}}

event: content_block_delta
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"Hello"}}

event: content_block_delta
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":" world"}}

event: content_block_stop
data: {"type":"content_block_stop","index":0}
</CodeBlock>

这是完整生命周期中的一个片段。

这里最重要的是：

**你不能简单地把 Anthropic SSE 的 `data` 当成 OpenAI 的 `choices[].delta` 来解析。**

需要根据事件名和 `delta.type` 分发。

不同的增量类型包括：

| `delta.type` | 含义 |
|---|---|
| `text_delta` | 文本增量 |
| `input_json_delta` | 工具调用参数的 JSON 字符串片段 |
| `thinking_delta` | 可见的推理摘要增量 |
| `signature_delta` | Thinking 签名相关数据 |

`input_json_delta` 中的 `partial_json` 可能只是一段不完整 JSON，因此流式处理工具调用时应累积后再解析。

此外，最终停止原因通常出现在 `message_delta` 中，而不是 `message_stop` 本身。流式过程中还可能出现 `ping` 和 `error` 事件。<Cite ref="turn618649search4"/>

## 七、Thinking：与 OpenAI Reasoning 的对应关系

在 OpenAI Responses API 中，你可能会看到 `reasoning` 类型的 Output Item，以及 `reasoning.effort` 一类控制参数。

Anthropic 也支持对应的 Thinking 能力，并且有较为明确的协议表达。

例如，在支持的 Claude 模型上，可以配置：

```json
{
  "thinking": {
    "type": "adaptive",
    "display": "summarized"
  }
}
```

这样 Claude 可以根据问题自行决定推理深度，并在支持的情况下返回推理摘要。

返回内容可能包含：

```json
{
  "content": [
    {
      "type": "thinking",
      "thinking": "A short reasoning summary...",
      "signature": "encrypted-signature..."
    },
    {
      "type": "text",
      "text": "The answer is 42."
    }
  ]
}
```

这里有三个容易忽略的细节：

1. `thinking` Block 不是最终回复的正文；`text` 才是通常要展示给用户的回答。
2. 返回的 Thinking 文本只是推理摘要，不是未经处理的完整内部推理。
3. `signature` 是需要按官方规则原样保留并回传的数据，尤其是在多轮工具调用场景中。

较早的 Claude 模型还支持通过 `thinking: {"type":"enabled","budget_tokens":...}` 指定推理预算。但新型号的支持情况已经发生变化，例如 Claude Opus 5.5 使用 Adaptive Thinking，不接受旧的手动 `budget_tokens` 配置。

因此不要假设所有 Claude 模型都接受完全相同的 Thinking 参数。<Cite ref="turn670425view0"/>

## 八、另外几个值得知道的特性

### 1. Structured Outputs

Anthropic 也支持 JSON Schema 约束输出，最新协议使用 `output_config.format`：

<CodeBlock language="json">
{
  "output_config": {
    "format": {
      "type": "json_schema",
      "schema": {
        "type": "object",
        "properties": {
          "answer": {
            "type": "string"
          }
        },
        "required": ["answer"],
        "additionalProperties": false
      }
    }
  }
}
</CodeBlock>

它与 OpenAI Responses 的 `text.format` 概念相近。生成的 JSON 会出现在 Claude 的 `text` Content Block 中。

Anthropic 的工具定义也支持 `strict: true`，用于约束工具调用参数。JSON 输出和 Strict Tool Use 解决的是不同的问题。<Cite ref="turn919162search3"/>

### 2. Prompt Caching

Anthropic 的 Prompt Caching 也值得特别关注。

对于长 System Prompt、RAG 上下文、长对话历史等复用场景，你可以在请求顶层指定：

```json
{
  "cache_control": {
    "type": "ephemeral"
  }
}
```

这是自动缓存模式。你也可以把 `cache_control` 放在特定 Content Block 上，明确指定缓存断点。

缓存的默认 TTL 是 5 分钟，也支持 1 小时选项。返回的 `usage` 会包含缓存创建和缓存命中相关的 Token 统计。

**注意：缓存不是对话状态。** 即使命中 Prompt Cache，你仍需要按照 Messages API 的规则构造完整上下文。缓存只是让重复上下文处理更高效。<Cite ref="turn104396search0"/>

### 3. 结束原因 Stop Reason

Anthropic 的 `stop_reason` 很值得专门处理，尤其在构建通用模型网关时。

| Anthropic | 含义 |
|---|---|
| `end_turn` | 模型正常结束当前回复 |
| `max_tokens` | 达到输出 Token 限制 |
| `tool_use` | 需要处理客户端工具调用 |
| `stop_sequence` | 命中自定义停止序列 |
| `pause_turn` | 服务端工具执行循环暂停 |
| `refusal` | 模型拒绝处理请求 |
| `model_context_window_exceeded` | 上下文窗口达到限制 |

它不与 OpenAI Chat Completions 的 `finish_reason` 完全一一对应。例如，Anthropic 对自定义停止序列和自然结束使用不同的原因值。

工程上需要根据 `stop_reason` 决定继续调用、执行工具、处理截断，还是结束当前任务。<Cite ref="turn919162search5"/>

### 4. 旧版 Completion 与参数兼容性

Anthropic 以前也有一个旧接口：

```http
POST /v1/complete
```

这是类似传统 Prompt-to-Text Completion 的接口，**现在已经标记为 Deprecated**，新项目应使用 Messages API。<Cite ref="turn104396search1"/>

另外，截至目前的官方文档，Claude 4.7 及以后的模型不再支持非默认的 `temperature`、`top_p` 和 `top_k` 采样配置；Claude 4.6 及以后的模型也不支持旧式 Assistant Prefill 技巧。迁移已有客户端时需要检查这些参数，避免 HTTP 400 错误。<Cite ref="turn251480view0"/>

## 九、如果你要实现一个同时支持 OpenAI / Anthropic 的客户端

建议不要直接在两套原始 JSON 之间进行简单的字段替换，而应该建立一个内部统一模型。

比如：

```typescript
type ContentPart =
  | { type: "text"; text: string }
  | {
      type: "tool_call";
      id: string;
      name: string;
      arguments: unknown;
    }
  | {
      type: "tool_result";
      callId: string;
      result: unknown;
    };

type UnifiedMessage = {
  role: "system" | "user" | "assistant" | "tool";
  content: ContentPart[];
};
```

这个定义只是简化的中间表示。如果支持 Thinking、图片、PDF、流式事件、并行工具调用等，还需要额外字段和类型，并保留不能丢失的供应商专有数据。

整体架构可以是：

<box border radius="lg" padding={3} gap={2}>
  <box align="center" gap={1}>
    <box background="surface-secondary" padding={3} radius="md" width="100%" align="center" gap={1}>
      **Application / Agent**
      <text color="secondary" size="xs">你的业务代码</text>
    </box>
    <icon name="arrow-down" color="tertiary"/>
    <box border={{size:1,color:"default"}} padding={3} radius="md" width="100%" align="center" gap={1}>
      **Unified LLM Abstraction**
      <text color="secondary" size="xs">Message、Content、Tool Call、Stop Reason、Stream Event</text>
    </box>
    <icon name="arrow-down" color="tertiary"/>
    <grid columns={3} gap={2}>
      {#each ["OpenAI Chat Adapter","OpenAI Responses Adapter","Anthropic Messages Adapter"] as name}
        <grid-item key={name}>
          <box background="surface-secondary" radius="md" padding={2} minHeight="76px" justify="center" align="center">
            <text textAlign="center" weight="medium" size="xs">{name}</text>
          </box>
        </grid-item>
      {/each}
    </grid>
  </box>
</box>

每个 Adapter 要负责转换四个重要方面：输入消息结构、输出类型化内容、工具调用往返、以及 Streaming 事件和结束状态。

## 十、最后帮你建立一个心智模型

理解这三套 API，其实可以从设计重心入手：

- **OpenAI Chat Completions**：围绕聊天消息和工具调用组织协议。
- **OpenAI Responses**：围绕一次模型响应以及其中的多种类型化 Items 组织协议，并提供更多服务端状态管理方式。
- **Anthropic Messages**：围绕单个 Assistant Message 及其内部的类型化 Content Blocks 组织协议；基础对话是无状态的。

如果你只记住最核心的一句话，我建议是：

**Anthropic Messages = Chat Completions 风格的对话管理 + Content Blocks 风格的结构化生成 + 一套独立的 Tool Use 和 Streaming 协议。**

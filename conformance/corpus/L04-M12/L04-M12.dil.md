我查了一下 MoonBit 目前的实现，发现你的想法其实已经有几种很接近的先例了。而且我觉得你提出的方向很值得探索，尤其是在 AI 生成代码越来越多的情况下。

**我的核心判断是：与其强迫 AI 写出每一行都适合人类阅读的代码，不如把代码分成两个层次：**

- **Contract / Specification（契约层）**：由人重点阅读和审查，包括函数签名、数据模型、不变量、行为约束、错误语义。
- **Implementation（实现层）**：允许 AI 生成较冗长的防御性代码、边界检查、异常处理和辅助函数，只要它满足上层契约。

但这里有一个关键区别：**公开 API 不一定等于真正值得 review 的核心逻辑。**

你希望审查的可能不仅是“这个函数输入输出什么”，还包括“它承诺做什么、依赖什么、哪些行为绝对不允许发生”。

下面先看 MoonBit 的机制，再对比其他语言。

## 一、MoonBit：你的记忆基本正确，但有三种不同机制

### 1. `.mbti`：自动生成的 API 摘要

普通 MoonBit 项目可以执行：

```bash
moon info
```

当前工具链会生成类似 `pkg.generated.mbti` 的接口文件，展示一个 package 对外暴露的类型、函数和方法签名。

它的用途很适合代码审查：你可以通过 Git diff 判断一次修改是否改变了公开 API。MoonBit 社区项目也确实有这样的实践。<Cite refs={["turn174266search16","turn174266search2"]}/>

但是，它不是最理想的**人工维护契约**：生成文件可能被覆盖，而且通常不包含足够丰富的业务行为描述。

### 2. `declare`：先写声明，再写实现

MoonBit 在 2026 年 1 月引入 `#declaration_only`，又在 2 月的 0.8.0 版本中将其替换为 `declare` 关键字。

官方明确把它定位为面向 AI 的 specification-first development：人先写声明和测试，让 AI 根据这些约束实现代码。<Cite refs={["turn363959search0","turn363959search1"]}/>

例如：

```moonbit
/// 根据规则计算最终价格。
/// 返回值不能小于零。
declare fn calculate_price(
  original : Int,
  discount : Int
) -> Int
```

然后可以在同一个 package 的其他源码位置提供匹配的实现：

```moonbit
fn calculate_price(
  original : Int,
  discount : Int
) -> Int {
  // 这里放完整的实现
  ...
}
```

MoonBit 官方说明，声明和实现必须在函数名称、可见性、泛型参数、参数、返回值和 effects 等方面一致。<Cite ref="turn363959search3"/>

所以，**它非常接近你设想的“声明与实现分离”**。

不过有个重要限制：目前的诊断文档还定义了 `declaration_implemented` 警告，即声明找到对应实现时，编译器可能认为声明已经多余。这意味着 `declare` 更偏向“先设计、后实现”的开发过程，而不是已经完全成熟的永久双文件契约机制。<Cite ref="turn174266search10"/>

### 3. Virtual Package：真正具有约束作用的接口文件

MoonBit 还有一个 2025 年引入的 experimental virtual package 机制。

它允许人工编写 `.mbti`，指定一个 package 必须提供的函数接口；实现可以在同一 package 中提供，也可以由其他 package 实现并在构建时替换。

编译工具会检查实现是否满足接口约束。<Cite refs={["turn174266search0","turn174266search1"]}/>

这在结构上比普通 `declare` 更接近传统的 Interface / Implementation Separation，不过官方仍将其标为实验特性，并说明目前 virtual package 仅支持普通函数。

我反而觉得，这里面可能隐藏着一个很有意思的语言设计取舍。

**OCaml 的 `.mli` 并不是一个失败的设计。恰恰相反，它非常成功。但 MoonBit 不完全照搬，可能是因为它想解决的问题、代码组织方式，以及它愿意让开发者付出的维护成本不同。**

而且你提到的背景很重要：MoonBit 的主要设计者张宏波确实曾是 OCaml 核心开发者，也是 ReScript/BuckleScript 的作者。<Cite ref="turn174266search0"/>

我没有找到他明确解释“为什么 MoonBit 不直接采用 OCaml `.mli` 机制”的一手表述。因此，下面需要区分已经确定的设计事实和我的推测。

## 1. 首先，OCaml 的 `.mli` 确实很好

我找到一段特别贴合你最初想法的讨论。

2018 年，OCaml 的主要设计者之一 <Entity category="people" value="Xavier Leroy" disambig="OCaml 编程语言设计者"/> 在社区解释为什么要把 `.mli` 和 `.ml` 分开。

他的主要理由不是类型检查，而是：

**接口文件代表模块使用者的视角，实现文件代表模块实现者的视角。**

他还特别强调了两个优点：

- 面向使用者的文档注释放在 `.mli`，实现细节的注释放在 `.ml`，避免两种信息混杂。
- `.mli` 可以按照最容易理解的顺序组织 API，而 `.ml` 必须考虑代码实现之间的依赖关系。

这几乎就是你想要的效果：让人类阅读的内容拥有一套独立于实现的组织方式。

原始讨论：[Xavier Leroy 在 OCaml 论坛的回复](https://discuss.ocaml.org/t/what-is-the-reason-of-separation-of-module-implementation-and-signatures-in-ocaml/1735/33)。<Cite ref="turn468731search14"/>

所以你的直觉是有历史依据的，而不是单纯因为 AI 代码越来越冗长才出现的新需求。

## 2. MoonBit 和 OCaml 最大的架构差别：文件是不是模块

OCaml 中，一个 `.ml` 文件通常就是一个模块，相应的 `.mli` 是它的接口。

MoonBit 则是 package 作为主要的组织单位，同一个 package 下的多个 `.mbt` 文件共享顶层定义。<Cite refs={["turn468731search5","turn174266search9"]}/>

这使得它们适合不同的分离方式。

假如 MoonBit 原封不动地采用 OCaml 的文件一对一接口制度，就会和它的 package 设计不太匹配。

当然，这**不能解释为什么不提供一个 package 级别的、人工维护的 `.mbti` 文件**。技术上完全可以设计这样的能力。

实际上，MoonBit 的 virtual package 已经支持一部分这种模式：人工编写 `.mbti`，再让实现满足这个接口，只是它主要定位于可替换的 package 实现，目前仍是实验性特性。<Cite ref="turn363959search0"/>

## 二、Cloudflare Access 其实比你想象的更适合做这件事

你担心的场景是：

> 我忘记给 Tunnel 配置 Access，或者某次更新把 Access 策略搞坏了，结果全世界都能直接向 Agent 发送指令。

这是非常合理的威胁模型。而 Cloudflare 恰好提供了两个很有用的防护机制。

### 第一层：强制所有域名都必须有 Access 保护

Cloudflare 在 2026 年新增了 **Require Access protection** 功能。

打开之后，没有配置匹配 Access 应用的域名会被默认阻止，而不是默认公开。<Cite refs={["turn662996search8","turn119338search0"]}/>

这正是为了防止你担心的「创建了 Tunnel 或 DNS 记录，却忘记配置身份验证」的问题。

### 第二层：让家里的 cloudflared 再次验证 JWT

这一点尤其值得你注意。

Cloudflare Tunnel 提供 **Protect with Access** 选项。开启后，家里运行的 `cloudflared` 也会验证请求携带的 Access JWT，验证通过才转发给 Agent Web 服务。<Cite refs={["turn119338search1","turn119338search5"]}/>

这几层防护的意义不同：

- Cloudflare Access 管理谁有权限访问。
- `cloudflared` 验证 JWT，避免仅因边缘访问配置失误就放行无凭据请求。
- 本地认证使用另一套凭据，防止 Cloudflare 策略意外放宽时 Agent 直接失守。
- Agent 运行权限限制攻击成功后的破坏范围。

注意，JWT 验证仍属于 Cloudflare 这套信任体系，**不能代替真正独立的第二层认证**。

## 三、我会怎样具体配置

对于你一个人使用的情况，我会这样设置：

1. **Access 只允许一个明确的身份**：例如自己的 Google 账号邮箱，而不是允许某个邮箱域名下的所有人；登录账号开启 Passkey 或 MFA。这里验证的是你指定的登录身份，不是简单地验证「拥有 Cloudflare 管理员账号」。
2. **开启 Require Access protection 和 Protect with Access**：一个在 Cloudflare 边缘默认阻止未保护的域名，一个在 Mac 上验证 Access JWT。
3. **Agent Web UI 只监听 `127.0.0.1`**：由本机 `cloudflared` 转发到它。不在路由器上做端口映射，也不允许局域网之外通过其他路径直接访问服务。
4. **保留独立的应用认证**：如果 Agent Web UI 自带可靠的登录功能，就保留。如果没有，可以在本机增加一个带认证功能的反向代理。不要只凭某个 HTTP Header 就认定请求合法。
5. **用陌生设备进行拒绝访问测试**：未登录、错误账号、无 JWT、未经授权的 API 和 WebSocket 请求都应该被拒绝；然后再测试自己的 iPhone 是否能正常使用。

Cloudflare Access 还支持缩短会话有效期。对于高权限 Agent，不建议长期保持几乎无需重新认证的会话。<Cite refs={["turn764879search6","turn187539search5"]}/>

如果你希望验证的不只是账号，**而是必须是你持有的 iPhone**，那就需要进一步使用客户端证书（mTLS）或设备状态校验。Cloudflare 有相应能力，但配置和套餐限制需要单独考虑。<Cite refs={["turn764879search9","turn764879search13"]}/>

## 🔍 各区块诊断

| 区块 | 占比 | 大小 | 问题诊断 |
|---|---|---|---|
| System Prompt | 12% | ~15.4K | 偏大，可能有冗余规则/示例 |
| **Tool Definitions** | **28%** | **~35.8K** | **高危**：工具数量或 schema 描述过于冗长 |
| **File Reads** | **45%** | **~57.6K** | **最危险**：整文件灌入，未做检索/切片 |
| Conversation | 15% | ~19.2K | 相对健康，但被前两者挤压 |

> 📌 经验法则：Tool Defs 应 <10%，File Reads 应 <25%，Conversation 应 ≥30%。

## ✂️ 裁剪建议（按 ROI 排序）

### 🥇 优先级 1：File Reads 45% → 20%（可省 ~32K）

这是**最大且最可优化**的一块。

- **不要整文件读入**：改成"符号级检索"——先 grep/搜索函数名、类名，再只读相关行段。
- **切片 + 摘要**：长文件先让模型输出结构化摘要（AST/目录树），原始内容按需分页读取。
- **RAG 化**：把长期参考的大文件放进向量库，用 top-k 检索代替全量灌入。
- **剔除无关文件**：审查是否读了 `node_modules`、构建产物、锁文件、测试夹具等。
- **压缩格式**：用"路径 + 行号范围 + 摘要"代替源代码原文；去掉空行、注释、license header。

### 🥈 优先级 2：Tool Definitions 28% → 12%（可省 ~20K）

- **精简 schema**：删除冗长的 `description`（模型能靠命名推断的别写长段落）；字段说明一句话封顶。
- **合并/裁剪工具**：低频工具（一周用不到一次）移出常驻，按需加载（tool 路由 / lazy load）。
- **去重与归一**：多个相似工具（如 `read_file` / `read_multiple_files`）合并为一个。
- **示例外置**：工具描述里的 few-shot 示例改为"仅在调用出错时注入"。
- **改用短名 + 枚举**：用 `enum` 约束而不是长文字说明可选值。

### 🥉 优先级 3：System Prompt 12% → 6%（可省 ~8K）

- 删除与具体任务无关的"人格包装"、冗长示例、重复强调的规则。
- 把"格式规范"改为结构化 schema 或输出校验器，而非自然语言长文。
- 分层：核心指令常驻，任务专属指令按任务注入。

### 🏅 优先级 4：Conversation 15% → 保持（0.5K 缓冲）

- 主动**压缩旧对话**：对超过 N 轮的历史做摘要（"前情提要"），保留最近 3~5 轮原文。
- 工具调用结果（尤其大 JSON）**不回灌全文**，只保留关键字段或用引用 ID 回查。

**一句话行动清单**：
1. 立刻把 File Reads 从整文件读改为**检索+切片**（省最多，风险最低）。
2. 精简 Tool schema 并把低频工具**懒加载**。
3. System Prompt **去冗余**。
4. 对话历史做**滚动摘要** + 工具结果不留全文。

# 三种 DIL（DOM-in-Loop）渲染方案对比

## 一、方案定义

| 方案 | 核心机制 |
|---|---|
| **iframe 沙箱** | 将待求值的模板/表达式放入独立 `<iframe>`，利用浏览器原生隔离（独立 JS 上下文、独立 DOM）完成渲染，主调方通过 `postMessage` 或同源 DOM 访问取结果 |
| **Web Worker 虚拟树** | 在 Worker 中求值表达式，产出**虚拟 DOM 树**（纯数据结构），回传主线程后再 diff/patch 到真实 DOM |
| **主线程 AST 求值** | 解析模板为 AST，在主线程直接做表达式求值 + 直接操作真实 DOM，无跨线程/跨上下文开销（如 Vue 运行时、模板编译器类实现） |

---

## 二、逐项优劣

### 1. iframe 沙箱

**优势**
- **隔离性最强**：独立 JS 全局、独立 document，天然阻断原型链污染、全局变量泄漏，安全性接近浏览器级别
- 实现心智负担低：模板可直接 `document.write`/innerHTML，浏览器帮你完成全部解析
- 调试直观：DevTools 中就是一棵独立页面树
- 崩溃容忍：iframe 内异常不拖垮主页面

**劣势**
- **性能差**：每个 iframe 都是独立渲染进程/文档上下文，创建销毁数百 ms 级；内存开销大（几十 MB 起）
- **通信昂贵**：`postMessage` 是结构化克隆，大量 DOM/数据往返成本高
- **同步性差**：跨上下文调用本质异步，难以做高频更新（拖拽、动画）
- **数量受限**：大量 iframe 会触发浏览器进程/内存上限，移动端尤其脆弱
- **样式/布局耦合**：iframe 内外尺寸、滚动、字体继承需手工桥接

**适用**：低频、强隔离需求（第三方不可信模板、用户上传的 HTML 片段预览）。

---

### 2. Web Worker 虚拟树

**优势**
- **主线程零阻塞**：表达式求值、模板解析全在 Worker，长模板/复杂表达式不卡 UI
- **CPU 密集友好**：可并行多 Worker 分片求值
- **数据结构纯净**：虚拟树是可序列化 JSON，天然可缓存、可快照、可 diff 前比较
- **隔离性中等偏好**：Worker 无 DOM，天然阻止"求值时误操作真实 DOM"的副作用
- **可测试性强**：虚拟树是纯函数输出，单测无需浏览器

**劣势**
- **序列化开销**：每次求值结果要结构化克隆过线，大树的往返成本随节点数线性增长；频繁全量渲染会抵消并行收益
- **双份 AST/树内存**：Worker 侧虚拟树 + 主线程真实 DOM + diff 中间态
- **diff/patch 仍需主线程**：真正落地 DOM 的开销没省，复杂 patch 仍可能卡顿
- **通信模型复杂**：需自建请求/响应/取消/背压协议，异步语义渗透到业务层
- **Worker 内无 DOM 相关能力**：依赖 `getComputedStyle`、布局度量的表达式无法求值，需回主线程补，形成往返

**适用**：模板求值 CPU 重、更新频率中等（表单、列表、报表）、希望把编译/求值逻辑与 UI 解耦的场景。

---

### 3. 主线程 AST 求值

**优势**
- **性能上限最高（同步路径）**：无跨上下文/跨线程通信，求值→创建节点→插入一气呵成，微秒~毫秒级
- **同步语义**：可读布局、可测量、可在同一帧内完成，适合动画/拖拽/高频更新
- **内存最省**：单份 AST + 直接产出真实 DOM，无中间树
- **生态成熟**：Vue/React 编译时优化即此路线，工具链、调试、错误栈都最完善
- **可做细粒度响应式**：依赖追踪精确到表达式，局部更新成本低

**劣势**
- **无隔离**：表达式在主线程求值，恶意/错误模板可触达全局（需自建作用域沙箱，如 `with`+Proxy 或解释器，仍非硬隔离）
- **阻塞主线程**：超大模板/死循环表达式会直接卡死页面（需自建超时/中断，JS 单线程难中断）
- **安全边界弱**：面向不可信输入时几乎不可接受

**适用**：自有可信模板、高频交互、对延迟敏感的核心渲染路径。

---

## 三、选型结论

**按"信任度 × 更新频率 × 隔离需求"三维决策：**

| 场景 | 推荐 | 理由 |
|---|---|---|
| 可信模板 + 高频/低延迟（核心 UI、动画、拖拽） | **主线程 AST 求值** | 同步路径无可替代，通信开销为零 |
| 可信模板 + 求值 CPU 重 + 中频更新（大表格、复杂表单、报表） | **Web Worker 虚拟树** | 把求值移出主线程，diff/patch 仍轻量 |
| 不可信输入 / 第三方模板 / 用户 HTML 片段 | **iframe 沙箱** | 唯一能提供硬隔离的方案，牺牲性能换安全 |
| 需要"求值隔离但又要高频" | **混合**：Worker 求值 + 主线程增量 patch，或 iframe 常驻复用（池化）而非重建 | 单一方案无法同时满足 |

**总体建议（默认选型）**：
1. **主路径用主线程 AST 求值**，作为 DIL 的默认渲染器——覆盖 80% 可信模板场景，性能与可维护性最佳。
2. **CPU 热点下沉 Worker**：把"表达式求值 / 模板编译"抽成纯函数，可平移进 Worker 产出虚拟树；主线程只做 patch，形成同一套 AST 的两条执行后端（`inline` / `worker`），按负载自动切换。
3. **iframe 仅作为"不可信内容"兜底**，且必须做**实例池化 + 生命周期复用**，避免频繁建销；通信走增量协议而非全量 `postMessage`。

**一句话结论**：*默认主线程 AST 求值保证延迟；重计算场景切 Worker 虚拟树后端；只有面对不可信输入才付 iframe 的隔离成本——三者共享同一 AST 前端，按信任度与负载动态路由。*
